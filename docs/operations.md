# Operations

This is the production reference. For a first local run, use the
[quickstart](quickstart.md); for component and trust-boundary context, read the
[architecture overview](architecture.md).

Shar's Rust and pure-JavaScript standalone servers use the same protocol,
configuration bundle, SQLite schema, and PostgreSQL state model. They may be
run interchangeably on a single host against one SQLite WAL database. SQLite
is not the HA deployment adapter: do not place the database on a network
filesystem or share it between machines. Both standalone servers also expose a
ten-connection PostgreSQL adapter and an optional Redis-compatible atomic
nonce/pressure adapter; live multi-host/failover validation remains a release
gate.

## Key material

Create a bundle on a trusted machine and keep it out of source control:

```sh
cargo run --release --bin shar-keygen -- --output shar-keys.json
chmod 600 shar-keys.json
```

Both key generators use 64 independent Miller–Rabin rounds for each 1024-bit
factor before constructing the 2048-bit modulus. This is defense-in-depth for
probable-prime generation, not a substitute for the independent cryptographic
review required before GA.

Both servers reject a Unix key file readable by group or other users. Back up
the file in an encrypted secret store; losing its RSW trapdoor makes outstanding
challenges unverifiable. Never log or expose `SHAR_SIGNING_SEED`,
`SHAR_RSW_LAMBDA`, `SHAR_NETWORK_SECRET`, `SHAR_FALLBACK_SECRET`, or
`SHAR_ADMIN_SECRET`, or `SHAR_SITEVERIFY_MASTER_SECRET`.

At startup, both implementations deterministically compare real sequential
squaring with protected trapdoor evaluation for the current RSW key and every
overlapping key. An inconsistent modulus/lambda pair is a fatal configuration
error and the process does not bind its listener. Do not bypass this failure or
discard the prior key during an active rotation: restore a known-good protected
bundle from backup. The check is deliberately outside readiness because no work
may be issued under suspect key material.

For signing-key rotation, deploy the new current key and list the old public
key in `SHAR_PREVIOUS_VERIFY_KEYS`. The bundled Rust and JavaScript tools can
produce those overlap lists atomically:

```sh
cargo run --release --bin shar-keygen -- rotate --input shar-keys.json --output shar-keys-next.json
npm run keygen:js -- rotate --input shar-keys.json --output shar-keys-next.json
```

Each command refuses to overwrite its output, preserves the network/fallback/
admin/site-verification secrets, and retains the previous signing key and RSW
trapdoor until all old challenges and verification tokens have expired. Deploy
the new bundle only after checking its mode-0600 permissions; first start it as
a readiness-gated canary so the trapdoor self-test runs, then run the standalone
interoperability test against the shared state during rollout.

The default Tier-32 lifetime estimate is about 509 days and the default maximum
is two years. Rotation automation must therefore retain every previous signing
key and RSW trapdoor through the greatest signed expiry actually issued under
that key; a routine short overlap is unsafe. Lowering a policy maximum affects
only new challenges and never permits removal of key material still referenced
by an unexpired quote.

## Standalone configuration

The principal settings are:

| Variable                        | Meaning                                                                                                                               |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `SHAR_KEY_FILE`                 | Mode-0600 JSON bundle generated by `shar-keygen`                                                                                      |
| `SHAR_ALLOWED_ORIGINS`          | Unique canonical comma-separated HTTPS origins; local HTTP is limited to localhost and loopback                                       |
| `SHAR_DATABASE`                 | SQLite file; defaults to `shar.sqlite` locally and `/data/shar.sqlite` in containers                                                  |
| `SHAR_POSTGRES_URL`             | PostgreSQL connection URL; when present, selects PostgreSQL instead of SQLite                                                         |
| `SHAR_POSTGRES_CA_FILE`         | Optional PEM CA certificate for the PostgreSQL server                                                                                 |
| `SHAR_REDIS_URL`                | Optional Redis-compatible URL used for nonce and pressure state; requires `rediss://` outside insecure development                    |
| `SHAR_REDIS_CA_FILE`            | Optional PEM CA certificate bundle for the Redis-compatible server; requires a `rediss://` URL                                        |
| `SHAR_FALLBACK_SECRET`          | Optional independent 32-byte base64url bearer secret for privileged host fallback completion                                          |
| `SHAR_FALLBACK_METHODS`         | Optional comma-separated advertised methods; requires the fallback secret and defaults to passkey/email/authenticated-session/support |
| `SHAR_PRESENCE_MODE`            | Browser-visible presence plan: `none` (default) or host-owned `host`                                                                  |
| `SHAR_ADMIN_SECRET`             | Optional independent 32-byte base64url bearer secret that enables the scoped policy API                                               |
| `SHAR_SITEVERIFY_MASTER_SECRET` | Required independent 32-byte master used to authenticate tenant/site-scoped final verification calls                                  |
| `SHAR_REGION`                   | Optional trusted deployment-region identifier bound into issued and verified envelopes                                                |
| `SHAR_ADMIN_ASSETS`             | Existing admin bundle directory; defaults to `dist/admin` locally, is canonicalized at startup, and is preconfigured in both images   |
| `SHAR_LISTEN`                   | Listen `host:port` on port 1–65,535; defaults to `127.0.0.1:8080`, with IPv6 addresses written in brackets                            |
| `SHAR_PREVIOUS_VERIFY_KEYS`     | JSON array of overlapping `{kid,x}` Ed25519 public keys                                                                               |
| `SHAR_PREVIOUS_RSW_KEYS`        | JSON array of overlapping `{id,modulus,lambda}` RSW keys                                                                              |
| `SHAR_TRUST_SEED`               | Optional 32-byte issuer seed for the blinded trust-credit profile                                                                     |
| `SHAR_TRUST_KEY_ID`             | Optional 1–32-byte base64url issuer identifier; configure together with `SHAR_TRUST_SEED`                                             |
| `SHAR_PREVIOUS_TRUST_KEYS`      | JSON array of overlapping `{seed,key_id}` blinded-credit issuer pairs                                                                 |
| `SHAR_TRUST_RETENTION_SECONDS`  | Optional 60-second–30-day trust-credit retention; defaults to 86400                                                                   |
| `SHAR_TRUSTED_PROXY_CIDRS`      | Optional comma-separated IPv4/IPv6 proxy CIDRs allowed to supply `X-Forwarded-For`                                                    |
| `SHAR_ASSURANCE_MODE`           | `off` (default) or `trusted-header`; the latter requires configured trusted proxy CIDRs                                               |
| `SHAR_REQUEST_LOG`              | `1` (default) emits privacy-safe JSON completion events; `0` disables them                                                            |
| `SHAR_MAX_CONCURRENT_REQUESTS`  | Per-process in-flight protocol/admin cap from 1–65,536; defaults to 256                                                               |
| `SHAR_STATE_TIMEOUT_MS`         | State connect/command/lock deadline from 100–60,000 ms; defaults to 5,000                                                             |
| `SHAR_REQUEST_BODY_TIMEOUT_MS`  | Total request-body intake deadline from 100–60,000 ms; defaults to 15,000 and never times out proof verification                      |
| `SHAR_SHUTDOWN_TIMEOUT_MS`      | Total SIGTERM drain/flush deadline from 6,000–300,000 ms; defaults to 25,000 and exits nonzero if forced                              |
| `SHAR_INSECURE_DEVELOPMENT`     | Set to `1` only for local evaluation; permits ephemeral keys and plaintext state services and must never be used in production        |

Both standalones fail startup with configuration status 78 when the admin
bundle root is missing, is not a directory, or names a filesystem root. Static
requests resolve their final canonical path and return 404 when a symlink would
escape the configured root.

Forwarding headers are ignored unless the immediate TCP peer is in
`SHAR_TRUSTED_PROXY_CIDRS`. When configured, Shar walks `X-Forwarded-For` from
right to left through the trusted proxy suffix and selects the first untrusted
address. A malformed chain falls back to the immediate peer. Configure only
proxies that overwrite, rather than append to, client-supplied forwarding
headers at the trust boundary.

Origin entries must equal the URL origin serialization exactly: no wildcard,
credentials, path, query, fragment, whitespace, duplicate, empty segment,
default port, or trailing slash is accepted. HTTP is permitted only for
`localhost`, `127.0.0.1`, and `[::1]`; production application origins use
HTTPS. Both standalones reject the entire configuration with `EX_CONFIG` if
any entry is invalid. `createSharHandler` applies the same validation to an
explicit `allowedOrigins` option; omitting the option intentionally disables
browser issuance.

The browser request body cannot choose `session_binding`; both standalone
servers discard that field before pricing. A trusted integration may have its
proxy overwrite `X-Shar-Session-Binding` and configure the proxy CIDR above.
Shar accepts that header only when the immediate peer is in the trusted CIDR
list, and binds the resulting value into the signed challenge. The Fetch
handler exposes the equivalent `sessionBinding` callback for applications that
provide their own trusted request context. Treat the header as a host-generated
hash, never as a browser or raw-session identifier.

Assurance mode is opt-in. With `SHAR_ASSURANCE_MODE=trusted-header`, an
immediately trusted proxy may overwrite `X-Shar-Assurance-Tier` with one
canonical decimal integer from 0 through 32. Both standalones remove or ignore
that header from every untrusted peer, always discard `assurance_tier` supplied
in the browser body, and fail startup if the mode has no configured proxy trust
boundary. Invalid trusted values fail with `invalid_assurance_tier`; absence
means no assurance contribution. The proxy must reduce its disclosed signals
to this tier and must not forward raw behavior, automation, user-agent, device,
or identity fields to Shar. Shar does not log the header or store those raw
inputs. A trusted tier changes only the newly issued quote. It persists as
decaying assurance pressure only when the host also supplies its opaque
`X-Shar-Session-Binding`; it is never consulted while redeeming or verifying a
completed quote. Keep the default `off` setting for privacy mode.

Keep `SHAR_FALLBACK_SECRET` separate from signing, RSW, and network-pseudonym
keys. Only a trusted host backend may call `/v1/fallback/complete`; never expose
the bearer value to browser JavaScript. Each call must use a unique, opaque
`assertion_id` after the host has verified the named passkey, email,
authenticated-session, support, or equivalent method. Shar consumes that id
atomically and returns the supplied tenant/site/action/origin bindings.
`SHAR_FALLBACK_METHODS` controls the bounded method list advertised with every
challenge and accepted by the privileged endpoint. Empty, duplicate, malformed,
or secretless lists fail startup. When no fallback secret exists, challenges
explicitly advertise `{ available: false, methods: [] }` and the widget does
not display a nonfunctional fallback control.

`SHAR_PRESENCE_MODE=host` advertises that the integrating host owns an optional
presence/session step; it never lets Shar classify or reject a proof. Use the
trusted `session_binding` integration above when the host needs that presence
result cryptographically bound to the issued challenge. `none` makes no browser
presence claim.

Derive a distinct final-verification credential for every tenant/site with
`shar-keygen site-secret` or `npm run site-secret`, and store it only in the
integrating application's backend secret store. The host supplies it in the
`secret` field accepted by JSON and compatibility form requests. Shar validates
the credential and signed tenant/site binding before consuming the token. Do
not distribute the master or a derived credential to frontend code. Rotating
the master invalidates all derived credentials, so coordinate application
secret rollout before changing it.

When `SHAR_ADMIN_SECRET` is unset, the policy API responds as an unknown route;
the static dashboard contains no secret or private configuration. When enabled,
serve Shar only behind HTTPS, restrict `/admin/` and `/v1/admin/` at the reverse
proxy to operator networks or identity-aware access, and enter the generated
base64url secret in the unlock dialog. The dashboard keeps the value only in
React state for the current tab: it does not use cookies, local storage, session
storage, or query parameters. Rotate it immediately if it appears in logs,
browser automation artifacts, or support captures. Policy saves affect only new
quotes; signed outstanding quotes retain their promised price and remain valid.

`GET /metrics` exposes four unlabeled OpenMetrics/Prometheus counters for
successful challenge issuance, redemption, final site verification, and host
fallback completion, plus `shar_audit_events_dropped_total`. Two cumulative
issuance-duration counters separately report pricing/challenge construction and
the complete challenge handler through response serialization. Divide either
duration by the corresponding issued-counter delta to obtain a window mean;
the metrics intentionally avoid per-scope histograms or labels. They contain no
tenant, site, action, IP, session, backend, or device labels. `GET /healthz` is
process liveness only.
Provisionable Prometheus rules and a Grafana dashboard live under
[`deploy/observability`](../deploy/observability/README.md). Their tests require
every query to reference a metric exposed identically by both servers and reject
privacy-sensitive dimensions. The Kubernetes example includes scrape
annotations, but operators must still configure an independent `/readyz` probe;
the Prometheus `up` series describes scrape reachability, not store readiness.
`GET /readyz` performs read-only probes against configuration, pressure, and
nonce storage and returns retryable `readiness_unavailable` with HTTP 503 when
required state cannot be reached. Audit storage is deliberately excluded:
audit is best-effort and cannot make a valid proof fail. Both container
healthchecks use readiness, while orchestrators should use `/healthz` for
liveness and `/readyz` for traffic admission.

Every standalone response includes a fresh `X-Shar-Request-Id`. With
`SHAR_REQUEST_LOG=1`, both servers emit one `request-observation-v1` JSON event
after each completed response containing only that identifier, a normalized
method and route, status, and integer duration in milliseconds. Unknown paths
become `unmatched` and all dashboard assets become `/admin/*`; query strings,
origins, addresses, forwarded headers, tenant/site/action, user agents, and
device data are never included. The runtime-neutral Fetch handler provides the
same header and an optional best-effort `observeRequest` callback. Callback or
logging failures cannot change a response or proof outcome. Send these events
to an access-controlled collector if longer retention or correlation is needed.

Both standalones bound in-flight protocol and admin requests with
`SHAR_MAX_CONCURRENT_REQUESTS`. Saturation returns HTTP 503 with
`capacity_unavailable`, `retryable: true`, `next_action: "retry"`, and a
one-second `Retry-After`; it never adds pressure debt or classifies the caller.
Liveness, readiness, and metrics bypass this admission gate so operators can
still distinguish a live, dependency-ready but saturated process. The Fetch
handler applies the same default per handler instance and exposes
`maxConcurrentRequests` for edge/platform integration. Tune the value below
the database/Redis and memory saturation point using load tests, and keep
connection, header, slow-client, and volumetric limits at the TLS proxy as an
independent outer boundary.

The Rust HTTP server runs synchronous cryptography and SQLite/PostgreSQL/Redis
operations on Tokio's blocking workers rather than request workers. Its
blocking-state admission is the smaller of the aggregate request cap and 64,
so an allowed 32-request burst can queue behind a ten-connection durable-store
pool without creating an unbounded blocking-worker backlog. Saturation or the
configured state deadline returns the same retryable operational error and
keeps its permit until the blocking operation actually exits. Readiness allows
only one dependency probe in flight so a hung store cannot accumulate probe
tasks. The JavaScript PostgreSQL and Redis adapters use their runtime's async
clients. Node's built-in SQLite adapter is synchronous and remains appropriate
for the documented single-host path; use PostgreSQL/Redis for multi-replica
deployments.

`SHAR_STATE_TIMEOUT_MS` bounds SQLite lock waits, PostgreSQL connection,
statement, client-query, lock, idle-transaction, and TCP-user waits, plus Redis
connection and command/read/write waits. A deadline failure flows through the
same retryable store/pricing/readiness error contracts; it is not recorded as
invalid work. This is only a state-operation deadline. Shar never imposes a
client proof-completion timeout, and an issued quote keeps its signed expiry.
Set the value above normal state-service p99 latency but below the upstream
request timeout, and coordinate it with PostgreSQL/Redis proxy limits.

Challenge pricing and outstanding-work reservation are one atomic store
operation in every built-in adapter. This prevents concurrent requests from
all purchasing work at the pressure tier they observed before any reservation.
External `PressureStore` implementations must provide the combined
`priceAndRecord`/`price_and_record` operation with equivalent isolation; both
public interfaces require it and provide no split compatibility fallback. A
storage failure returns a retryable pricing error and must not issue unsigned
or unreservable work.

SQLite keeps an `outstanding_counts` acceleration row beside the authoritative
per-quote outstanding rows. Both servers create it automatically and initialize
existing scopes from those rows during startup after an upgrade. Database
triggers maintain the counter for every insert and deletion, including expiry
cleanup, successful completion, and expired-proof removal, inside the same
`BEGIN IMMEDIATE` transaction. This avoids split application updates and keeps
the issuance hot path constant-time. Do not manually edit either table; restore
them together from the same backup if database recovery is required. Drain old
processes before deploying the trigger-backed schema so a pre-upgrade process
cannot also apply its former application-side counter update.

Outcome updates identify the completed quote by its signed expiry and remove
one matching row. PostgreSQL uses the same scoped exact-expiry deletion under a
row lock, Redis removes one sorted-set member at the exact score, and the
in-memory stores remove one matching value. This matters when a higher-tier
quote has a longer lifetime but completes before an older, cheaper quote.

The Fetch handler enforces the 16 KiB request limit from the declared
`Content-Length` and from a bounded Web Streams reader, so chunked requests
cannot force the runtime to buffer an unbounded body before Shar rejects it.
Both standalone transports enforce the same ceiling before constructing the
runtime-neutral request. The JavaScript server rejects an oversized declared
length before reading, drains the input, and also stops a chunked stream at the
ceiling; the Rust body collector is bounded at the transport layer. Early 413
responses retain `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`,
the request id, and readable CORS headers for an allowed browser origin.
Its `allowedOrigins` option is an exact allowlist; omitting it disables browser
issuance rather than enabling wildcard CORS.

Blinded trust credits are opt-in and use a separate issuer seed. Configure the
current and overlap variables together, and review the disclosed scope and
retention in [`trust-credits.md`](trust-credits.md). A pressure-store failure
after the durable one-shot token consume is intentionally non-fatal; it cannot
turn a valid credit into a lost retry.

The authenticated `/admin/` dashboard's Operations view combines those
counters with liveness and discovery-key counts. It is an aggregate process
view: values reset on restart, carry no scope labels, and do not replace
privacy-filtered scoped audit events or an external readiness/metrics system.

With `SHAR_ADMIN_SECRET` enabled, `GET /v1/admin/audit` returns at most 100
newest `audit-v1` events for the exact `tenant`, `site_key`, and `action` query
scope. The dashboard's Audit events view uses this endpoint. It is deliberately
not a cross-tenant export: storage adapters hash or filter the scope before
reading, and the response contains only the privacy-filtered audit fields.

The stores also retain privacy-filtered `audit-v1` events for 24 hours. These
events are scoped to tenant/site/action and may include outcome code, work tier,
rendering backend, and timestamp only. They intentionally omit origin, session
binding, network pseudonym, address, user-agent, and device data. Audit writes
are best-effort; a full audit store must not reject a valid proof.
The standalones queue at most 4,096 events and coalesce up to 128 over a bounded
10 ms window when the adapter supports batching. Queue overflow and persistence
failures increase
`shar_audit_events_dropped_total`; alert on any increase, but do not turn that
alert into proof rejection. SQLite batches insertions and retention pruning in
one transaction so audit retention does not serialize every proof-critical
state operation behind a separate writer transaction. Redis groups each batch
by its privacy-safe action hash slot, allocates one contiguous sequence range,
and uses one multi-member sorted-set write per Lua invocation. This retains
cluster compatibility and event uniqueness without per-event Redis calls.

For PostgreSQL, both servers require TLS 1.2 or newer and verify the server
certificate and hostname. The Rust URL must explicitly contain
`sslmode=require`; the JavaScript server forces certificate verification even
if the URL omits it. Use `SHAR_POSTGRES_CA_FILE` for a private CA. Only an
explicit `SHAR_INSECURE_DEVELOPMENT=1` process may use
`sslmode=disable`, which exists for isolated local and CI service containers;
never set it in a deployed environment. The adapters
create `shar_*` tables and constraints on startup. Do not declare HA ready until
concurrent replay, database restart, failover, and network-partition tests pass
against the exact PostgreSQL service and proxy used in production.

When `SHAR_REDIS_URL` is set, Redis replaces only nonce consumption and
pressure state; policy configuration remains in the selected SQLite or
PostgreSQL store. Redis keys hash session and network inputs, share a cluster
hash slot only within one tenant/site/action scope, and expire after two idle
days by default. The production URL must use `rediss://`. Both servers verify
the certificate and hostname, require TLS 1.2 or newer, and accept a private CA
bundle through `SHAR_REDIS_CA_FILE`. Supplying that variable with a plaintext
URL is a startup error. Validate Lua `EVAL`,
`SET ... EXAT NX`, hashes, sorted sets, and cluster hash tags against the exact
Redis-compatible service before enabling it.

The Rust standalone enables `TCP_NODELAY` on every Redis connection and every
accepted HTTP connection because quote issuance is a latency-sensitive series
of small request/response messages. Preserve that behavior in sidecars and
proxies; transport coalescing delays can dominate the atomic script itself.
Both standalones fail the request that observes a dropped Redis connection and
never replay its potentially applied mutation. Rust discards that pool entry
and reconnects it on the next independent operation; the JavaScript standalone
uses a bounded 50–1,000 ms reconnect delay with offline queuing disabled. The
request gate and state deadline bound concurrent recovery pressure. Readiness
returns to healthy after the store is reachable again without restarting Shar.
The Rust PostgreSQL pool follows the same no-replay boundary: a terminated
backend makes the observing readiness probe fail, that probe prepares a fresh
configured TLS/deadline-bound client, and the next independent probe or request
can succeed. PostgreSQL mutations are never automatically replayed.

Run real atomic-store races against staging services before deployment:

```sh
SHAR_TEST_POSTGRES_URL='postgresql://shar:...@db.example/shar' \
SHAR_TEST_REDIS_URL='rediss://:...@redis.example:6379' \
npm run test:stores:live
```

For a disposable environment that supplies both services, run the stronger
dual-process test as well:

```sh
SHAR_TEST_POSTGRES_URL='postgresql://shar:...@127.0.0.1/shar?sslmode=disable' \
SHAR_TEST_REDIS_URL='redis://127.0.0.1:6379' \
npm run test:standalone-external-interop
```

That test starts both optimized standalones against PostgreSQL configuration
and Redis atomic state, races redemption and final verification across them,
restarts both processes, and completes work issued before the restart. The
plaintext example is valid only for isolated test services because the script
sets insecure-development mode internally.

The same disposable services can run the deterministic partition gate (local
ports 45432 and 46379 must be free):

```sh
SHAR_TEST_POSTGRES_URL='postgresql://shar:...@127.0.0.1/shar?sslmode=disable' \
SHAR_TEST_REDIS_URL='redis://127.0.0.1:6379' \
npm run test:standalone-store-partition
```

This starts both optimized standalones behind a test-only TCP fault proxy,
severs all established PostgreSQL and Redis sockets, silently blackholes new
connections, and restores them without restarting either server. It requires
liveness to remain available, readiness and challenge issuance to return their
exact bounded retryable errors, recovery to restore issuance, and both
standalones to shut down cleanly. It validates Shar's client behavior under a
complete local connection partition; it does not validate replication,
election, DNS, TLS, or proxy behavior of a specific managed service.

Before pointing a deployment at managed state, run the local verified-TLS gate:

```sh
npm run test:standalone-store-tls
```

It creates disposable pinned PostgreSQL and Redis containers plus an ephemeral
private CA. The gate exercises both stores directly and both optimized
standalones without insecure-development mode, then proves that wrong trust
roots, hostname mismatches, and plaintext production URLs never become ready.
It validates Shar's TLS clients and configuration contract; it does not replace
failover and certificate-rotation trials against the exact managed service.

Set `SHAR_TEST_POSTGRES_TLS=0` only for an isolated local PostgreSQL process
that has no TLS support. The harness creates the `shar_*` schema, uses unique
test scopes, asserts exactly one winner among 64 concurrent nonce consumers,
reconnects each configured client/pool and confirms that the first consumed
nonce remains rejected, and exercises pressure issuance/failure/success. These
local tests are not substitutes for service-specific replicated failover and
production-TLS testing.

## Containers

The images run as UID/GID 10001, store default SQLite state under `/data`, expose
port 8080, and handle `SIGTERM` by draining connections and closing their state
connections. Both images serve the same compiled dashboard at `/admin/` with a
same-origin-only content-security policy.
The Compose example removes Linux capabilities, sets a read-only root
filesystem, uses an in-memory `/tmp`, and binds the service to loopback.

```sh
export SHAR_KEY_FILE="$PWD/shar-keys.json"
export SHAR_ALLOWED_ORIGINS="https://app.example"
docker compose -f deploy/docker/compose.yaml up --build
```

The local Compose implementation must support secret `uid`, `gid`, and `mode`
fields. Before first production deployment, confirm inside the container that
`/run/secrets/shar_keys.json` is owned by UID 10001 and has mode 0400.

The [Kubernetes example](../deploy/kubernetes/README.md) uses two replicas,
separate startup/liveness/readiness probes, a disruption budget, non-root and
read-only security contexts, and external PostgreSQL/Redis state. Replace all
example image and service values, then validate the exact storage and proxy
failure modes before treating it as production configuration.

## Backup and shutdown

Use SQLite's online backup API or a database-native backup command while the
service is live; do not copy only the main file while WAL data may be pending.
Restore into a staging instance first and run the interoperability check. Stop
containers with `SIGTERM` and set the orchestrator grace period longer than
`SHAR_SHUTDOWN_TIMEOUT_MS` (the examples use 30 seconds for the 25-second
default). Both standalones stop request admission first and reserve the final
five seconds for flushing the bounded audit queue and closing
SQLite/PostgreSQL/Redis clients. If accepted requests consume the earlier drain
budget, remaining connections are closed, cleanup still runs, and the process
exits nonzero within the total deadline. Audit timeout or persistence failure is
reported or counted but never changes a proof result; a client that loses a
response during forced termination can request a new quote.

Two servers sharing keys and one SQLite database can be checked with:

```sh
SHAR_ENDPOINT_A=http://127.0.0.1:8080 \
SHAR_ENDPOINT_B=http://127.0.0.1:8081 \
npm run test:interop
```

The check verifies cross-server issuance/redemption, atomic replay exclusion,
final verification, and the ability to obtain new work after a replay.
